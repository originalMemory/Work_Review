## Context

Work Review 是一个 Tauri 2 桌面应用，后端 Rust、前端 Svelte 4，数据存储在本地 SQLite（`workreview.db`）+ JPEG 截图文件中。当前所有数据仅存在于单台设备，无任何网络同步能力。

用户拥有多台设备和一台 24h 在线的 Unraid NAS（可运行 Docker），希望各设备的工作轨迹数据自动汇聚到 NAS，每台设备本地都能看到合并后的完整视图。

完整设计背景见 `docs/SYNC_DESIGN.md`。

## Goals / Non-Goals

**Goals:**

- 多台桌面客户端的活动记录、日报、摘要可通过 NAS 中转实现增量同步
- 截图文件可按需同步（支持原图 / 缩略图 / 不传三种模式）
- 同步对现有功能零侵入：不开启同步时行为完全不变
- sync-server 足够轻量，Docker 单容器部署即可运行

**Non-Goals:**

- 不做 Web 查看端（未来规划）
- 不做实时推送（分钟级轮询即可）
- 不做多用户权限体系
- 不做端到端加密

## Decisions

### 1. 中央枢纽模式（NAS 做服务端）vs 点对点同步

**选择**：中央枢纽。

**理由**：设备之间不需要互相发现，NAS 24h 在线天然适合做汇聚点。点对点（如 CRDT）实现复杂度高，且依赖设备同时在线。

**替代方案**：Syncthing 直接同步文件 → 否决，SQLite 文件级同步会导致数据库损坏。

### 2. UUID v7 作为全局记录标识

**选择**：每条活动记录在创建时生成 UUID v7，取代自增 `id` 用于跨设备去重。

**理由**：UUID v7 时间有序，既能做唯一标识又保持插入顺序；自增 id 在多设备间必然冲突。本地 `id` 仍保留用于内部引用，`uuid` 用于同步层。

**替代方案**：`{device_id}_{local_id}` 组合键 → 可行但不如 UUID 通用，且增加查询复杂度。

### 3. SQLite 作为服务端数据库

**选择**：sync-server 使用 SQLite（WAL 模式）。

**理由**：个人使用场景（2-5 台设备，分钟级同步），SQLite 的写入吞吐完全够用。部署极简，无需额外数据库服务。每年数据量约 4GB，远低于 SQLite 舒适上限。

**替代方案**：PostgreSQL → 过重，个人场景不需要；后续如有 Web 端或高并发需求可迁移。

### 4. 冲突策略：Last-Write-Wins + UUID 去重

**选择**：
- 不同设备的记录天然不冲突（uuid 唯一）
- 同一条记录被 `merge_activity` 更新时，以 `timestamp` 更大的版本为准
- 日报 / 摘要按 `(date, device_id)` 分别保留；其中 `device_id=''` 表示“全部设备”的综合日报

**理由**：工作记录是追加型数据，几乎不存在两台设备同时修改同一条记录的场景。Last-Write-Wins 简单可靠。日报除了保留各设备独立版本外，还需要支持“全部设备”视角下的单张综合卡片。把综合日报也存进同一张日报表，并使用空 `device_id` 作为标识，可以复用现有缓存、同步、导出与读取链路，避免单独维护另一张聚合表。

### 5. 截图路径加 device_id 前缀

**选择**：`screenshots/{device_id}/YYYY-MM-DD/HHmmss.jpg`

**理由**：避免不同设备在同一秒产生的截图文件同名冲突。服务端和客户端使用相同路径结构。

### 6. 同步协议：HTTP REST + Bearer Token

**选择**：axum HTTP 服务，核心接口包括 `push`、`pull`、设备列表，以及单文件截图上传/下载接口，统一使用 Bearer token 认证。

**理由**：REST 简单、调试方便、防火墙友好。个人使用单 token 足够。截图上传最初采用 multipart 批量上传，但在实际联调中出现客户端与服务端解析兼容问题，因此改为：

- `PUT /api/sync/screenshot/{device_id}/{date}/{filename}`：单文件二进制上传
- `GET /api/sync/screenshot/{device_id}/{date}/{filename}`：单文件下载

这种方式更直观，跨端行为更稳定，也更便于后续排障。sync-server 只监听 HTTP，外网访问由用户自行通过 Lucky 等工具反代 + TLS，项目内不处理。

### 7. 合并查看方式：设备筛选下拉列表

**选择**：概览页、时间线和日报页顶部增加设备下拉列表，默认「全部设备」合并展示，也可选择单台设备筛选。

**理由**：用户既需要全局视角了解所有设备的工作轨迹，也需要单设备视角排查某台机器的使用详情。下拉列表操作成本低，不需要额外页面。设备列表展示优先使用 `device_name`，无名称时回退 `device_id`。其中日报页在“全部设备”模式下不再按设备分栏，而是优先展示一张综合日报卡片。

### 8. 离线策略：静默跳过 + 下次补推

**选择**：同步失败时静默记录日志，不弹窗不打扰，下次定时触发时自动补推。

**理由**：本地数据完整性不依赖同步，且 NAS 通常高可用，短暂中断无需用户干预。

### 9. 同步粒度：全量不过滤

**选择**：不支持按时间段或工作日过滤，全量同步所有数据。

**理由**：个人使用场景数据量可控，过滤逻辑增加复杂度但收益有限。

### 10. 远端截图下载策略：按保留期自动拉取

**选择**：客户端在 pull 数据后，自动下载保留期内的远端截图；保留期使用本地 `screenshot_retention_days` 配置。

**理由**：如果完全按需下载，跨设备浏览时间线时首次打开体验较差；如果无条件全量拉取，又会把 NAS 上的所有截图都重新拉到本地。按本地保留期自动拉取可以在体验和磁盘占用之间取得平衡。

**补充实现**：下载列表直接从本次 pull 返回的活动记录中提取，避免每次同步后再扫描整张本地活动表。

### 11. 设置页设备标识展示：以后端规范化结果为准

**选择**：`save_config` 返回后端规范化后的完整配置，前端保存成功后用返回值刷新本地状态。

**理由**：`device_id` / `device_name` 可能在后端 `normalize()` 阶段补齐。如果前端只提交原始配置而不回收后端结果，首次进入设置页时会出现字段为空、退出重进后才显示的体验问题。

### 12. 综合日报存储策略：`device_id=''`

**选择**：在日报表中直接存储综合日报，使用 `device_id=''` 代表“全部设备”视角。

**理由**：这样可以复用现有 `(date, locale, device_id)` 唯一键和同步模型，不必新增聚合日报专用表，也不需要为读取接口引入新的返回类型。前端只要在“全部设备”模式下优先读取空 `device_id` 的日报即可。

**生成策略**：

- 当用户在“全部设备”模式下生成日报时，基于该日期全部设备的活动数据生成内容
- 生成结果保存为 `device_id=''` 的日报记录
- 当用户在“全部设备”模式下打开日报页时，优先读取 `device_id=''` 的综合日报
- 若该日期尚无综合日报，则页面保持“暂无日报”状态，是否生成由用户手动触发

### 13. 日报导出命名策略：文件名带设备标识

**选择**：自动保存和手动导出的 Markdown 文件名统一包含设备标识。

**命名规则**：

- 综合日报：`<date>.all.md`
- 单设备日报：`<date>.<device_id>.md`

**理由**：用户可以为不同设备或“全部设备”分别生成同一天的日报。如果仍使用 `<date>.md`，后一次导出会覆盖前一次结果。将 `device_id` 直接体现在文件名中，可以在不增加目录层级的前提下避免覆盖，也更便于在文件管理器中直接辨认来源。

## Risks / Trade-offs

**[首次全量同步可能很慢]** → 分批推送（每批 500 条），截图按需传输，避免一次性传输大量数据。

**[NAS 不可达时数据丢失]** → 不会丢失。客户端始终本地先存，同步失败时静默记录日志、不弹窗，下次定时触发自动补推。本地数据完整性不依赖同步。

**[截图存储空间膨胀]** → 服务端永久保留所有截图（NAS 存储充裕）；客户端继续维持原有的保留天数清理逻辑，仅清理本地数据。

**[数据库 schema 迁移风险]** → 使用 `ALTER TABLE ADD COLUMN`（SQLite 支持），失败时静默跳过（已有列则忽略），与现有迁移策略一致。

**[merge_activity 导致同步遗漏]** → 推送时按 `timestamp > last_push_timestamp` 查询，`merge_activity` 会更新 `timestamp`，因此被合并的记录也会被捕获。

## Resolved Questions

- **首次同步**：全量推送所有历史数据。`last_push_timestamp` 初始为 0，首次同步时所有记录都会被推送（分批，每批 500 条）。
- **删除同步**：不做。客户端的本地清理（清除历史、保留天数清理）仅影响当前设备，不同步到其他设备和 NAS。NAS 作为归档中心永久保留数据。

- **合并查看方式**：设备下拉列表，默认全部设备，可选单设备筛选。
- **离线容忍**：静默跳过 + 下次补推，不弹窗。
- **日报合并**：日报由用户手动生成（AI/模板），按 `(date, device_id)` 保留；单设备日报使用具体 `device_id`，综合日报使用 `device_id=''`。日报页面默认展示综合日报，也支持切换到单设备查看对应日报。
- **外网访问**：项目内不处理，用户自行通过 Lucky 反代 + TLS；sync-server 只监听 HTTP。
- **同步粒度**：不需要，全量同步。
